# ⚡ Кэширование промптов в LLM: механизм и практическая проверка

> [!abstract] Суть
> **Prompt caching** позволяет повторно использовать вычисления для уже обработанного префикса запроса. Оно может уменьшить задержку обработки входа и стоимость повторных обращений, но не сохраняет ответы или память пользователя и не гарантирует попадание в кэш.

Заметка выросла из [объяснения Avi Chawla](https://x.com/_avichawla/status/2044670188998803855?s=46). Сейчас это поддерживаемая памятка; конкретные условия Anthropic ниже сверены с официальной документацией **31 октября 2026 года**. Для другого провайдера проверяй его правила отдельно.

---

## 🧠 Что переиспользуется

При обработке запроса модель сначала читает вход (**prefill**), затем генерирует новые токены (**decode**). Если начало следующего запроса уже обработано, сервер может использовать сохранённое вычислительное состояние префикса — например KV-cache — и обработать только новый хвост.

Cache hit не означает, что весь запрос выполнен: новая часть входа и генерация ответа остаются работой модели. Отсюда нельзя вывести «мгновенный отклик» или фиксированный процент экономии для любой сессии.

Это также не retrieval и не долговременная память. Приложение по-прежнему передаёт нужный контекст; кэш оптимизирует его обработку, а не вспоминает сведения, отсутствующие в запросе.

## ⚙️ Правила на примере Anthropic

По [официальной документации prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching):

- Кэширование в Messages API включается через `cache_control`: автоматически для растущего контекста либо явными breakpoints на блоках.
- Префикс собирается в порядке **tools → system → messages**. Это порядок API, а не рекомендация вставлять определения tools внутрь system prompt.
- Запись на **5 минут** стоит 1,25× базового входа; на **1 час** — 2×. Тариф cache read зависит от модели: универсального коэффициента «в десять раз дешевле» нет.
- Минимальная длина кэшируемого префикса зависит от модели. Слишком короткий блок может не дать cache hit.
- Изменение блока до выбранной границы меняет ключ соответствующего префикса. Более ранний записанный префикс иногда ещё можно использовать; это не обязательно промах для всего запроса.
- В usage доступны `cache_creation_input_tokens` и `cache_read_input_tokens`. Проверяй их, а не делай вывод об использовании кэша по одному времени ответа.

Это условия конкретного API. TTL, поддерживаемые модели, цены, порядок блоков и поведение автоматического кэширования нельзя переносить на другой сервис по аналогии.

## 🛠 Как расположить данные

Стабильные материалы ставь перед часто меняющимися внутри структуры, которую допускает API:

```text
tools: неизменные определения инструментов
system: правила задачи
messages:
  стабильный документ или справочник
  [граница кэширования]
  новый вопрос и изменившиеся данные
```

Это схема, не выполненный пример запроса. В реальной интеграции нужны корректные типы блоков и параметры выбранного API.

Например, ассистент отвечает на вопросы по одной версии инструкции. Сам документ сохраняется без изменений, новый вопрос идёт после него. Если инструкция обновилась, старый префикс больше не соответствует новой версии — правильность ответа важнее сохранения cache hit.

Не помещай меняющуюся дату, случайный идентификатор или динамическое имя пользователя перед большим стабильным документом без необходимости. Не переставляй tools между запросами произвольно. Но и не удаляй важные изменения из входа ради экономии.

## 💰 Как проверить экономию

Считай отдельно обычный вход, запись кэша, чтение кэша и выход. Эти категории нельзя бездумно складывать с общим числом входных токенов: сначала выясни семантику usage у провайдера. Формула обычного входа и cache read разобрана в [[Справочник LLM API]].

Условный пример для **одинакового префикса**: при цене записи 1,25× и выбранном тарифе чтения 0,1× две обработки стоят `1,25 + 0,1 = 1,35` вместо `2` условных единиц обычного входа. Это арифметическая иллюстрация, не действующий прайс и не измерение Claude Code. Новый хвост, выход модели и другие платные операции здесь не учтены. Если повторного чтения не будет, запись с наценкой может оказаться дороже обычного входа.

Перед включением в рабочий процесс:

1. Зафиксируй модель, версию документа и стабильную часть запроса.
2. Выполни несколько разрешённых тестовых запросов с одинаковым префиксом.
3. Сопоставь usage, фактическую стоимость и задержку; учитывай промахи и истечение TTL.
4. Измени документ и проверь, что система использует новое содержание.
5. Сравни стоимость принятого результата, а не только цену входных токенов.

В этой памятке интеграция не запускалась. Кэш не исправляет неверные данные, не гарантирует качество ответа и не заменяет проверку условий хранения данных у выбранного провайдера.
