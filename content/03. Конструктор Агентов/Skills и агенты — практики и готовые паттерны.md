# Skills и агенты — практики и готовые паттерны

> [!abstract] С чего начать
> Возьми одну повторяющуюся задачу, опиши входные материалы, порядок работы и проверяемый результат. Попробуй инструкцию в чате. Когда она помогает на реальных задачах, оформи её как skill.
> Отдельного агента добавляй, когда есть самостоятельная подзадача, из которой основному помощнику нужен только результат.

Здесь — общие практики написания skills и инструкций для агентов: планирование, сбор информации, подготовка результата, проверка и делегирование. Их можно применять к разным задачам независимо от роли. Примеры показывают, как использовать эти схемы на практике. Разницу понятий см. в [[Prompt vs Skill vs Agent vs Hook]].

## Базовые правила написания

| Что описать           | Полезная формулировка                                            |
| :-------------------- | :--------------------------------------------------------------- |
| Когда применять       | «Когда нужно превратить продуктовую идею в черновик требований»  |
| Какие материалы нужны | «Описание идеи, текущий процесс, ограничения и шаблон команды»   |
| Что делать            | «Уточни цель → изучи материалы → подготовь требования → проверь» |
| Что вернуть           | «Сценарии, критерии приёмки, источники и открытые вопросы»       |
| Где границы           | «Не придумывай бизнес-правила. Не меняй задачи в трекере»        |
| Когда работа готова   | «Для каждого сценария есть проверяемый ожидаемый результат»      |

Пиши конкретные действия. Вместо «ты лучший аналитик, тщательно всё изучи» — «найди противоречия, укажи источник каждого и вопрос для уточнения». Длинные справочники выноси в отдельные файлы и указывай, когда их читать. Это соответствует [рекомендациям Agent Skills](https://agentskills.io/skill-creation/best-practices).

## Какой паттерн выбрать

Паттерн — готовый порядок действий. Названия P1–P5 ниже — локальные обозначения этой заметки, чтобы на них удобно ссылаться.

| Ситуация | Паттерн |
| :--- | :--- |
| Обычная задача на несколько шагов | [P1 — базовый цикл](#p1-план--факты--результат--проверка) |
| Работа долгая, нужно продолжать в другой сессии | [P2 — память в файлах](#p2-план-и-находки-в-файлах) |
| Нужно описать фичу до разработки | [P3 — работа от требований](#p3-сначала-договориться-о-результате) |
| Есть черновик, нужно найти пробелы | [P4 — проверка по критериям](#p4-автор-и-проверяющий) |
| Нужно изучить большой объём отдельных материалов | [P5 — делегирование](#p5-поручить-подзадачу-и-собрать-результат) |

Для начала хватит P1. Остальные добавляй по необходимости; проходить все пять для каждой задачи не нужно.

## P1. План → факты → результат → проверка

**Когда:** готовишь требования, сравниваешь варианты или анализируешь проблему.

```text
1. Уточни цель и формат результата. Наметь 3–5 шагов.
2. Изучи доступные материалы. Раздели факты, предположения и пробелы.
3. Подготовь результат, опираясь на найденное. Дай ссылки на источники.
4. Проверь результат по исходной задаче: что покрыто, что противоречит
   источникам, что осталось неизвестным. Исправь найденные ошибки.
Если неизвестное меняет решение — задай конкретный вопрос.
Если не мешает продолжить — явно укажи ограничение результата.
```

**Пример:** для оплаты по ссылке изучить текущую оплату, описать основной сценарий и ошибки, затем проверить, что у каждого сценария есть ожидаемый результат.

Это наша простая схема для старта. План здесь — короткий список действий; для небольшой задачи отдельный файл и согласование каждого шага не нужны.

## P2. План и находки в файлах

**Когда:** задача занимает несколько сессий или включает много источников.

В [Planning with Files](https://github.com/OthmanAdi/planning-with-files) используются три основных файла: `task_plan.md`, `findings.md`, `progress.md`. Идея — сохранять состояние работы вне переписки.

| Файл | Что хранить |
| :--- | :--- |
| `task_plan.md` | Цель, этапы и статус каждого |
| `findings.md` | Факты со ссылками, ограничения и принятые решения |
| `progress.md` | Что выполнено, что проверено и с чего продолжить |

Готовая инструкция для упрощённого варианта:

```text
Веди план, находки и прогресс в трёх файлах в папке этой задачи.
После значимого этапа обновляй статус и сохраняй выводы со ссылками.
Перед продолжением работы прочитай эти файлы.
Не повторяй завершённые шаги без причины. Устаревшие выводы исправляй.
Итоговый документ храни отдельно от рабочих записей.
```

**Пример:** анализировать несколько платёжных интеграций два дня, затем продолжить с сохранённых выводов. Эти три файла — схема конкретного подхода, а не обязательный стандарт для всех skills.

## P3. Сначала договориться о результате

**Когда:** продуктовую идею нужно превратить в понятную задачу для разработки и QA.

В [OpenSpec](https://openspec.dev/docs/quickstart) идея сначала превращается в материалы для обсуждения, затем реализуется, а по завершении обновляется спецификация. В стандартной схеме выделены четыре вида материалов: замысел, требования, техническое решение и задачи. Это не «четыре плана». [Схема OpenSpec](https://openspec.dev/docs/schemas/spec-driven).

Для начала можно использовать упрощённый вариант без установки OpenSpec:

```text
1. Зачем: опиши проблему пользователя, цель и границы изменения.
2. Что: опиши новое поведение, ошибки и критерии приёмки.
3. Как: зафиксируй известные технические ограничения.
   Вопросы реализации, требующие инженера, вынеси отдельно.
4. Задачи: разложи согласованное изменение на разработку и QA.
До реализации разреши вопросы, которые меняют поведение продукта.
После реализации сверь фактическое поведение с требованиями
и обнови описание согласованных изменений.
```

**Пример:** до разработки оплаты по ссылке определить поведение при истечении срока и повторном открытии уже оплаченной ссылки. Значения сроков берём из согласованных правил, а не из догадок AI.

Для небольшой фичи достаточно разделов одного документа. Этот шаблон заимствует идею работы от требований; он не воспроизводит весь процесс и формат OpenSpec.

Полный процесс, артефакты и ограничения разобраны в [[OpenSpec]].

## P4. Автор и проверяющий

**Когда:** есть черновик и понятные критерии проверки.

```text
Подготовь черновик, затем проверь его отдельным проходом:
- соответствует ли он исходной задаче;
- подтверждаются ли утверждения источниками;
- описаны ли ошибки и граничные случаи;
- можно ли проверить каждый критерий приёмки.
Верни конкретные замечания с указанием проблемного места.
Исправь существенные замечания и повторно проверь исправления.
Ограничься двумя циклами; оставшиеся проблемы перечисли явно.
```

**Пример:** проверить требование «ссылка должна быстро открываться». Проверяющий отмечает, что не определены время и условия измерения; автор выносит их на уточнение.

Проверку может выполнить тот же помощник или отдельный агент. Второй агент полезен для отдельного прохода, но не гарантирует истинность выводов: нужны источники и реальные проверки. Это адаптация подхода [Evaluator–Optimizer](https://www.anthropic.com/engineering/building-effective-agents).

## P5. Поручить подзадачу и собрать результат

**Когда:** основному помощнику нужна короткая сводка из большого объёма материалов.

```text
Выдели самостоятельную подзадачу. Передай отдельному агенту:
- цель и нужные вводные;
- материалы или пути к ним;
- границы действий;
- формат результата и критерий завершения.
Получи выводы со ссылками, проверь их и включи в общий результат.
Если делегирование недоступно, выполни подзадачу сам и сообщи об этом.
```

**Пример:** основной помощник пишет требования, а подагент изучает документацию оплаты и возвращает таблицу «ограничение → источник → влияние на фичу».

Разные исследования можно поручать параллельно, если они не зависят друг от друга. Два помощника, одновременно переписывающие один документ, создают лишние конфликты. Подход соответствует схеме [Orchestrator–Workers](https://www.anthropic.com/engineering/building-effective-agents).

## Два шаблона для старта

Это текстовые заготовки, которые нужно адаптировать к своим материалам. Они не устанавливают skills и агентов автоматически.

### Пример skill — подготовка требований

Минимальное содержимое `SKILL.md`:

```markdown
---
name: feature-spec
description: Готовит черновик требований из продуктовой идеи. Используй, когда нужно описать сценарии и критерии приёмки перед разработкой.
---

# Подготовка требований

Вход: описание идеи, материалы о текущем поведении, шаблон команды.
Если материалов нет, уточни, где их взять, или явно ограничь черновик.

Порядок:
1. Уточни цель, пользователя и границы задачи.
2. Изучи материалы, выпиши подтверждённые ограничения со ссылками.
3. Подготовь сценарии, ошибки и критерии приёмки.
4. Проверь полноту и противоречия. Неизвестное вынеси в вопросы.

Результат: черновик требований и список вопросов для согласования.
Готово, когда у каждого сценария есть проверяемый ожидаемый результат
или явно указано, какого решения не хватает.
Не придумывай бизнес-правила и не публикуй задачи в трекере.
```

Пример запроса: «Используй feature-spec для оплаты по ссылке. Описание идеи и документация — в приложенных файлах». Сначала навык нужно разместить в поддерживаемом приложением каталоге: [[Форматы и размещение Skills]].

### Пример агента — исследователь ограничений

Это инструкция для отдельного помощника; поля настройки агента зависят от приложения.

```text
Задача: найти ограничения текущей системы, влияющие на новую фичу.
Вход: описание фичи и список документов для изучения.
Действия: читай материалы, сопоставляй утверждения, отмечай противоречия.
Границы: только чтение; не меняй файлы и не назначай бизнес-правила.
Результат: таблица «ограничение → источник → влияние на фичу»
и список вопросов, на которые в материалах нет ответа.
Готово: изучены переданные материалы или явно перечислены недоступные.
Верни основному помощнику краткий итог со ссылками, без полного журнала поиска.
```

Пример запроса основному помощнику: «Поручи отдельному агенту исследовать ограничения по этой инструкции. Затем учти выводы при подготовке требований».

## Как ссылаться на паттерны

В Obsidian можно дать ссылку прямо на раздел:

```text
[[Skills и агенты — практики и готовые паттерны#P1. План → факты → результат → проверка]]
```

Но название «P1» само по себе не передаёт инструкцию AI. Если используешь паттерн в skill, скопируй нужный блок в `references/patterns.md` внутри папки навыка и напиши в `SKILL.md`:

```text
Перед работой прочитай references/patterns.md, раздел P1.
Выполни его шаги для подготовки требований.
Перед выдачей результата примени проверку из раздела P4 того же файла.
```

Для разового запроса можно приложить эту заметку и назвать раздел. Для агента без доступа к файлу вставь нужный паттерн прямо в поручение.

## Как проверить свою инструкцию

Попробуй её на трёх задачах: обычная фича, фича с недостающими данными и запрос вне назначения навыка. Посмотри, соблюдает ли помощник формат, отмечает ли неизвестное и не применяет ли процедуру там, где она не нужна. Исправляй конкретные сбои в инструкции.

Для начала возьми **шаблон skill + P1**. Если результат требует отдельной проверки — добавь **P4**. Файлы состояния и дополнительных агентов подключай, когда задача стала достаточно большой.
