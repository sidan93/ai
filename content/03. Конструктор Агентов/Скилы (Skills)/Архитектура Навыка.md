# Архитектура навыка

> [!abstract]
> Минимальный файловый skill — директория с `SKILL.md`. Дополнительные references, scripts и assets нужны только тогда, когда улучшают выполнение или экономят контекст.

## Типичная структура

```text
my-skill/
├── SKILL.md              # метаданные, триггеры и основной маршрут
├── references/           # справочники и подробные инструкции
├── scripts/              # повторяемые проверки и преобразования
└── assets/               # шаблоны и материалы для результата
```

Названия дополнительных каталогов зависят от среды. Важнее, чтобы `SKILL.md` явно говорил, какой файл читать или запускать и в какой ситуации.

## Frontmatter

Для файлового формата Agent Skills базовое описание выглядит так:

```yaml
---
name: knowledge-base-editor
description: Проверяет и обновляет Markdown-базу знаний; используй для редакторского аудита, терминологии, frontmatter и внутренних ссылок.
---
```

- `name` должно быть коротким, устойчивым и различимым.
- `description` отвечает сразу на два вопроса: **что делает** навык и **когда его применять**.
- Дополнительные поля считай платформенными: проверяй их поддержку в своём клиенте.

Слишком общее описание вызывает ложные срабатывания. Описание без триггеров делает хороший навык почти невидимым.

## Основная инструкция

Практичная последовательность разделов:

1. **Назначение** — наблюдаемый результат.
2. **Когда использовать** — запросы и условия запуска.
3. **Когда не использовать** — соседние задачи и границы.
4. **Входы** — обязательные файлы, данные и решения пользователя.
5. **Процедура** — действия в правильном порядке.
6. **Инструменты** — разрешённые tools и предпочтительный способ применения.
7. **Безопасность** — ограничения, секреты и подтверждения.
8. **Проверка** — команды, инварианты и Definition of Done.
9. **Fallback** — что делать без сети, зависимости или доступа.

## Инструменты и зависимости

Карта ниже описывает возможности (capabilities), которые skill может использовать. Она не означает, что инструмент установлен, доверен или нужен каждому агенту.

В инструкции навыка лучше написать «нужен поиск с URL и датой публикации», чем жёстко привязать процесс к одному серверу. Конкретную реализацию вынеси в зависимости или адаптер среды.

| Capability | Для чего | Возможная реализация | Основной риск |
| :--- | :--- | :--- | :--- |
| Файлы | читать и менять рабочие материалы | [[Filesystem MCP]] или native filesystem tools | выход за разрешённый каталог |
| Веб-поиск | находить актуальные источники | [[Brave Search MCP]] или hosted search | недоверенный контент |
| Браузер | работать с динамическими страницами | [[Playwright MCP]] или computer use | prompt injection и side effects |
| Память | сохранять устойчивые факты | [[Memory MCP]] или собственное хранилище | утечка и устаревание данных |
| Репозитории | issues, PR, code search | [[GitHub MCP]] или GitHub API | запись не в тот repository |
| Календарь | читать доступность и создавать события | проверенный Calendar server/API | приглашения и изменение расписания |
| Выполнение кода | проверять и преобразовывать данные | shell, sandbox, code interpreter | запуск недоверенного кода |
| Декомпозиция | вести явный рабочий план | native reasoning или [[Sequential Thinking MCP]] | лишний контекст без улучшения результата |

### Как описывать зависимость

```markdown
## Зависимости

- Обязательно: чтение Markdown в пределах выбранной папки.
- Опционально: веб-поиск для проверки изменившихся фактов.
- Запрещено: публикация и удаление без отдельного запроса.
- Fallback: без сети пометить факты, требующие актуализации.
```

Такой контракт переносится между клиентами лучше, чем список конкретных команд.

### Полезные связки

#### Исследование

`search → открыть первичный источник → сопоставить дату → сохранить вывод → проверить цитаты`

Браузер нужен только для страниц, которые нельзя надёжно прочитать обычным fetch/search.

#### Работа с кодом

`найти правила проекта → прочитать код → изменить минимальный scope → formatter/test → diff review`

Отдельный reasoning server не обязателен: ценность создают проверяемые шаги и инструменты разработки.

#### Операционная задача

`прочитать состояние → подготовить preview → получить подтверждение → выполнить → перечитать результат`

Подтверждение должно находиться перед реальным side effect, а не в начале всей задачи.

### Проверка нового инструмента

1. Определи минимальную capability.
2. Проверь издателя, код, зависимости и обновления.
3. Ограничь каталог, account, repository, toolset или OAuth scope.
4. Проверь read-only сценарием.
5. Проверь ошибку и отзыв доступа.
6. Только затем разрешай изменяющие операции.

Подробнее: [[Выбор и проверка MCP-сервера]] и [[Безопасность MCP]].

## Что выносить из SKILL.md

| Материал | Куда | Зачем |
| :--- | :--- | :--- |
| Большой справочник | `references/` | не засорять контекст каждого запуска |
| Детерминированная проверка | `scripts/` | получать воспроизводимый результат |
| Шаблон документа | `assets/` | не генерировать структуру заново |
| Секрет | secret store / env | не хранить ключи внутри skill |
| Постоянное правило проекта | project instructions | применять независимо от выбранного skill |

## Правила для scripts

- предпочитай маленькие scripts с одной ответственностью;
- опиши вход, выход и код возврата;
- используй dry-run для изменяющих операций;
- не скрывай сетевые запросы или удаление файлов;
- фиксируй зависимости и минимальные версии;
- не печатай secrets в stdout и логи.

## Definition of Done

Критерии описывают состояние результата:

- обязательные поля присутствуют;
- изменены только файлы в области задачи;
- ссылки разрешаются;
- тесты и форматтер проходят;
- внешние утверждения имеют источники;
- значимые side effects подтверждены;
- пользователь получил путь к артефакту или краткий отчёт.

«Выглядит правильно» и «агент закончил работу» не являются проверками.
