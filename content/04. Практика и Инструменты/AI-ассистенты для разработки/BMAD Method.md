# BMAD Method — разработка через skills и артефакты

> [!abstract] Суть
> **BMAD Method** — набор skills, специализированных ролей и рабочих процессов для разработки с AI coding-agent. Он помогает явно оформить требования и решения, передать их между сеансами, реализовать изменение и проверить результат.

BMAD работает поверх coding tool: задаёт процедуру и контекст его работы. Если нужен SDK для исполнения агентов внутри собственного приложения, это другая инженерная задача. Здесь главный вопрос — как организовать разработку вместе с агентом и сохранить принятые решения.

---

## 🏗 Из чего состоит

| Элемент | Что делает |
| :--- | :--- |
| **Skills** | Описывают конкретную процедуру: исследование, спецификацию, реализацию или ревью |
| **Специализированные роли** | Добавляют продуктовую, архитектурную, UX- и инженерную перспективу, когда она нужна задаче |
| **Workflow** | Определяет порядок шагов, входы, результаты и точки принятия решений |
| **Файловые артефакты** | Сохраняют требования, спецификации, архитектурные решения, планы и состояние работы для следующих сеансов |
| **Вспомогательные скрипты** | Поддерживают настройку и выполнение процедур; требования к среде зависят от выбранной версии |

Роль задаёт способ рассмотрения задачи. Само наличие нескольких ролей не доказывает независимость ревью или параллельное исполнение: это зависит от workflow и возможностей coding tool.

---

## ⚙️ Как выбирается глубина процесса

BMAD предлагает подбирать объём подготовки под размер работы и неопределённость, а не создавать полный комплект документов для каждой правки.

- **Очевидная малорисковая правка:** можно обойтись обычным запросом coding-agent без BMAD.
- **Понятное изменение на один сеанс:** передать намерение в `bmad-build`; тот изучает контекст, планирует, реализует и проверяет изменение.
- **Неопределённая задача:** сначала провести нужное исследование или уточнить продуктовую идею.
- **Крупная работа:** зафиксировать общие требования и решения, разбить работу на части, реализовывать и проверять их последовательно.

В стабильном снимке v6.12.4 понятное намерение можно оформить через `bmad-spec`, затем передать в `bmad-build`. PRD, UX и архитектура нужны там, где они разрешают реальные вопросы или согласуют несколько участников. Список planning skills — набор инструментов, а не обязательная линейная цепочка.

## 📋 Пример: импорт банковского CSV

> [!example] Иллюстрация, не проверено запуском
> BMAD не устанавливался и не выполнялся для этого примера. Ниже показано возможное применение метода, а не отчёт об эксперименте.

Допустим, coding-agent должен добавить импорт операций в трекер расходов.

1. **Зафиксировать результат:** какие CSV принимаются, как распознаются даты и суммы, что считается дублем и как показываются ошибки строки.
2. **Разрешить неизвестное:** изучить реальные форматы файлов; при необходимости записать решение о нормализации данных.
3. **Оформить единицу работы:** например, импорт одного формата с явными критериями готовности и границами.
4. **Реализовать:** передать согласованное намерение и документы в Build.
5. **Проверить:** обычный файл, повторный импорт, неверную дату, пустую строку и частично ошибочный файл.

Следующий сеанс получает сохранённые правила импорта вместо устного пересказа предыдущего чата. Для исправления одной подписи в форме такой объём подготовки, скорее всего, избыточен.

## 🛠 Когда имеет смысл

- Требования и ограничения теряются между чатами или исполнителями.
- Над одной инициативой работают несколько человек либо агентов, которым нужны общие решения.
- Изменение затрагивает продукт, архитектуру и реализацию одновременно.
- Нужно разделить подготовку, выполнение и приёмку с понятными результатами этапов.

Начни с одного реального изменения и оцени качество результата, стоимость согласований и объём поддерживаемых документов. Это критерии выбора, а не подтверждённое преимущество BMAD над обычным coding-agent.

Это сравнение зафиксированных источников, не обещание, что плавающая документация или следующая версия сохранят те же команды. Прошедшая прогнозная дата релиза в README не подтверждает выход стабильной v7.

Для stable README указывает Node.js 20.12+, Python 3.10+ и uv; нужен совместимый AI coding tool. Установка здесь не проверялась. Перед внедрением сверяй инструкции именно выбранной линии.

Дополнительные skills и документы требуют времени, контекста и сопровождения. Подготовленная спецификация может оказаться неверной, а ревью агента — пропустить дефект. Тесты и проверка исходного пользовательского результата остаются необходимыми. Этот обзор не измерял ускорение, экономию токенов или превосходство качества.

## 🧭 Где заканчивается автономность

`bmad-build-auto` выполняет **одну единицу реализации**: уточняет намерение, создаёт или продолжает спецификацию, реализует, проверяет и записывает конечный статус. По stable-документации ему нужна возможность запускать subagents; без неё workflow останавливается.

Выбор следующей задачи, повторение по backlog и расписание принадлежат человеку либо внешнему оркестратору. Сохранённое состояние и unattended worker сами по себе не создают таймер, уведомления или разрешение на публикацию. Для автоматизации нужно отдельно определить запуск, полномочия, возобновление и проверяемый результат.
