# OpenSpec

> [!abstract] Суть
> **OpenSpec** — инструмент и workflow для spec-driven development: согласовать изменение поведения системы, реализовать его с coding-agent и сохранить актуальные specs. Основные результаты работы — Markdown-документы в репозитории, которые читают и редактируют человек и агент.

Главный вопрос OpenSpec: **что именно должно измениться и по каким сценариям мы примем результат?** Проект ориентирован в том числе на brownfield — изменения уже существующего кода, требований и ограничений.

---

## 🏗 Specs и changes

OpenSpec разделяет описание принятого поведения и ещё не завершённые изменения:

```text
openspec/
├── specs/                         # действующие требования по capabilities
│   └── report-export/spec.md
└── changes/
    ├── add-export-filter/         # предложение и delta specs одного изменения
    └── archive/                   # история завершённых изменений
```

**Specs** описывают наблюдаемое поведение: входы, результаты, ошибки, ограничения и проверяемые scenarios. **Change** содержит предложение изменить это поведение и связанные материалы для реализации. Внутри change лежат delta specs: какие требования добавляются, меняются или удаляются.

Так можно обсудить новое правило до изменения основных specs. После завершения работы delta переносится в актуальные specs, а change сохраняется в archive. Качество этого описания зависит от проверки людьми и сопоставления с кодом: документ сам по себе не доказывает, как система работает.

## 📋 Четыре вида артефактов

В стандартной schema `spec-driven` у каждого документа свой вопрос:

| Артефакт | Что в нём фиксируется |
| :--- | :--- |
| `proposal.md` | **Зачем:** проблема, границы, новые или меняемые capabilities и затронутые системы |
| `specs/<capability-path>/spec.md` | **Что:** изменение поведения, требования и конкретные scenarios |
| `design.md` | **Как:** технические решения, альтернативы, ограничения и риски |
| `tasks.md` | **Что выполнить:** implementation checklist с проверкой результата задач |

Например, «при пустом результате экспорт возвращает файл только с заголовками» относится к spec; выбор CSV-библиотеки — к design; реализация и проверка этой ветки — к tasks.

В schema proposal предшествует specs и design; они могут готовиться в любом взаимном порядке, затем формируются tasks. При этом документы можно уточнять по мере исследования и реализации. Design создаётся, когда нужны технические решения; для изменения без нового поведения допускается явное `skip_specs: true` в metadata change. Эти исключения не предназначены для сокрытия неописанных требований.

## ⚙️ Рабочий цикл

1. **Explore:** изучить код, ограничения и варианты вместе с агентом. Если изменение уже понятно, можно начать с propose.
2. **Propose:** создать change и материалы для обсуждения. Код ещё не является результатом этого шага.
3. **Review:** прочитать proposal, requirements/scenarios и tasks; исправить неверные допущения до реализации.
4. **Apply:** агент читает change и выполняет задачи, отмечая прогресс в `tasks.md`. Новые знания могут потребовать корректировки документов и продолжения работы.
5. **Archive:** после принятия результата обновить основные specs и перенести папку change в archive.

Это итеративный цикл с зависимостями между артефактами. Вернуться к требованиям или design при обнаружении ошибки — нормальная часть процесса.

**Archive обновляет документы OpenSpec; Git merge и deployment выполняются отдельно.** Галочки в tasks также нужно сверять с реально выполненными проверками, а не принимать за доказательство готовности.

## 🛠 Пример: фильтр периода для экспорта

> [!example] Иллюстрация, не проверено запуском
> OpenSpec для этого примера не устанавливался и не выполнялся. Показан принцип постановки изменения, а не готовая инструкция интеграции.

В отчёте уже есть CSV-экспорт. Требуется экспортировать только записи выбранного периода.

- В **proposal** описываем потребность и границы: добавить фильтр, сохранить прежний формат колонок.
- В **delta spec** фиксируем, какие записи попадают в результат, включаются ли обе граничные даты и что делать при пустом периоде. Правило timezone нужно согласовать, а не придумать агенту.
- В **design**, если он нужен, записываем решение, где применяется фильтр и как сохраняется совместимость существующего API.
- В **tasks** перечисляем реализацию и проверки: обычный период, граничные даты, отсутствие записей и неверный диапазон.

После apply проверяем поведение на согласованных данных. При archive delta становится частью текущей spec экспорта, а обсуждение изменения остаётся в истории.

## 🧭 Версия и вызовы в coding tools

Актуально на **2026-10-27**: **OpenSpec v1.15.0**, выпущенный 2026-10-24. Доступные вызовы зависят от версии CLI, выбранного profile и coding tool.

В README используется каноническая форма `/opsx:propose <change-name>`. В **Codex** предложение вызывается через skill **`$openspec-propose`**; документация также предлагает выбрать skill через интерфейс Codex. Копировать slash-команду из примера другого инструмента без проверки интеграции не следует.

Profile **default** включает explore, propose, apply и archive. **Expanded** добавляет более подробные процедуры, включая verify и incremental planning. Отдельный `/opsx:verify` — дополнительный workflow; проверка реального результата приложения нужна независимо от наличия этой команды.

**`openspec validate` проверяет материалы OpenSpec, а функциональные тесты приложения выполняются отдельно.** Формально корректная spec может содержать неверные требования. Для обзора прочитаны документы и schema; установка, CLI-команды и поведение агентов не испытывались.

## ⚠️ Когда полезен и что требует внимания

- Полезен, когда фичу нужно согласовать между разработкой, QA и владельцем продукта либо сохранить требования между сеансами coding-agent.
- Особенно уместен, если меняется существующее поведение и важно явно увидеть delta, совместимость и пограничные случаи.
- Для очевидной локальной правки документы могут добавить лишнюю работу. Выбирай минимальный объём, который делает результат проверяемым.
- Агент способен точно выполнить ошибочно сформулированную spec. Источники требований, спорные решения и критерии приёмки требуют человеческой ответственности.
- Specs нужно поддерживать после изменений кода: наличие папки `openspec/` не обеспечивает актуальность автоматически.
- Это open-source проект под MIT. Стоимость и возможности используемого coding tool и моделей определяются их условиями.

Сравнивай методологии по рабочему фокусу: [[BMAD Method]] охватывает более широкий процесс разработки через роли, skills и артефакты; [[Engineering Loop]] задаёт дисциплину инженерного сеанса; OpenSpec делает центральной единицей согласуемое изменение поведения и его отражение в specs. Этот обзор не измерял их скорость или качество относительно друг друга.
